# DOCX/Word OOXML: compatibilidad mínima para LumenCAT

Investigación documental de fuentes primarias y lectura del parser actual. No se ejecutó Microsoft Word ni se validaron documentos de terceros; las conclusiones de compatibilidad visual requieren una prueba posterior en Word real.

## Hallazgos priorizados

1. **DOCX es un paquete OPC, no un único XML.** Word guarda un ZIP con partes XML, un manifiesto `[Content_Types].xml` y archivos `.rels` que enlazan partes. El contenido principal de WordprocessingML se organiza como `document/body` con párrafos `p`; historias independientes como headers, footers, notas, comentarios, text boxes y glossary pueden guardar contenido fuera de `word/document.xml`. No basta con extraer el texto de esa parte para afirmar compatibilidad total. [Microsoft: estructura del paquete y stories](https://learn.microsoft.com/en-us/office/open-xml/about-the-open-xml-sdk), [Microsoft: estructura WordprocessingML](https://learn.microsoft.com/en-us/office/open-xml/word/structure-of-a-wordprocessingml-document), [ECMA-376](https://ecma-international.org/publications-and-standards/standards/ecma-376/).

2. **Los runs son unidades de formato y fragmentos de texto, no necesariamente segmentos lingüísticos.** Un párrafo contiene uno o más `r`; cada run agrupa texto con propiedades comunes (`rPr`), y puede incluir uno o varios `t` además de saltos, campos y otros elementos. Word puede dividir una oración en varios runs por estilo, énfasis, cambios de idioma, edición o contenido inline. Si LumenCAT concatena runs y reconstruye texto plano, pierde formato; si traduce cada run como segmento independiente, puede romper la sintaxis y el flujo lingüístico. La frontera correcta para la primera compatibilidad usable es conservar cada párrafo como segmento y exponer las fronteras/runs como códigos inline protegidos. [Microsoft: párrafos, runs y partes](https://learn.microsoft.com/en-us/office/open-xml/word/structure-of-a-wordprocessingml-document), [Microsoft: explicación de `Run`](https://learn.microsoft.com/zh-tw/office/open-xml/word/working-with-runs).

3. **El texto visible no siempre es texto `w:t`.** Tabuladores y saltos se representan con elementos como `w:tab` y `w:br`; hyperlinks relacionan contenido con otra parte/recurso; campos pueden contener instrucciones `w:instrText`, marcadores `w:fldChar` y un resultado visible cacheado en `w:t`; tracked changes y controles estructurados encapsulan texto con semántica adicional. Esas construcciones necesitan política: texto traducible, código protegido o rechazo explícito. No deben convertirse a espacios ni borrarse silenciosamente. [Microsoft: SDK para buscar y reemplazar en WordprocessingML](https://learn.microsoft.com/en-us/office/open-xml/word/how-to-replace-text-in-a-word-document-with-sax), [Microsoft API: `FieldChar`](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.fieldchar?view=openxml-3.0.1), [Microsoft: `fldSimple`](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oe376/955994f3-3b4f-4bf6-8133-3db8ed986d7f), [Microsoft: hyperlink](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oi29500/cc9e4bbd-134f-4d35-b2c7-95fde8c633a7).

4. **Word usa el formato Open XML por defecto, pero eso no garantiza que un editor externo preserve todas sus capacidades.** Microsoft recomienda `.docx` como formato Open XML predeterminado y observa que otras aplicaciones pueden leer solo partes del archivo o perder formato/funciones. La compatibilidad práctica exige round-trip del paquete y validación de documentos creados/guardados en Word. [Microsoft Support: formatos Open XML](https://support.microsoft.com/en-us/office/vba/open-xml-formats-and-file-name-extensions), [Microsoft Support: formatos de archivo](https://support.microsoft.com/en-us/office/collab-files/learn-about-file-formats).

5. **Transitional y Strict son variantes distintas.** Microsoft indica que Strict es un subconjunto de Transitional, elimina características heredadas y usa namespaces distintos (`purl.oclc.org/ooxml`). El Open XML SDK puede leer Strict mediante mapeo de namespaces; `src/formats/docx.rs` solo admite ahora Transitional con `http://schemas.openxmlformats.org/wordprocessingml/2006/main`. Para salida compatible con DOCX ordinario guardado por Word, Transitional es un corte inicial razonable; aceptar Strict debe ser una ampliación explícita, no interpretar ambos como si compartieran namespace. [Microsoft: SDK y Strict](https://learn.microsoft.com/en-us/office/open-xml/about-the-open-xml-sdk), [ECMA-376 partes y ediciones](https://ecma-international.org/publications-and-standards/standards/ecma-376/).

6. **El prefijo XML no es la identidad del namespace.** `w`, `x` u otro prefijo ligado a la misma URI es semánticamente equivalente; el prefijo es un alias. El parser actual exige prefijo literal `w:` en `word/document.xml`, raíz `w:document` y atributos `xmlns:w`. Por ello rechaza XML equivalente que use otro prefijo o namespace por defecto. `quick-xml` ya ofrece `NsReader` para resolución de namespaces; conviene comparar URI + nombre local, no prefijos textuales. [W3C Namespaces in XML](https://www.w3.org/TR/REC-xml-names/), [quick-xml `NsReader`](https://docs.rs/quick-xml/0.38.3/quick_xml/reader/struct.NsReader.html).

7. **El SDK oficial manipula estructura; no es un renderizador de Word.** Open XML SDK ofrece APIs tipadas para partes/elementos, edición, búsqueda y validación de esquema. Microsoft documenta que no reemplaza Word, no garantiza por sí solo la validez del archivo, y no brinda comportamiento de aplicación como la función de layout de Word. Su validador informa errores estructurales/esquema, no garantiza que Word muestre la página igual que antes. El SDK es .NET; integrarlo desde este binario Rust implicaría añadir un runtime/sidecar/IPC y más superficie de despliegue. [Microsoft: consideraciones de diseño del SDK](https://learn.microsoft.com/en-us/office/open-xml/open-xml-sdk-design-considerations), [Microsoft: validación](https://learn.microsoft.com/en-us/office/open-xml/word/how-to-validate-a-word-processing-document), [repo oficial: API de bajo nivel y prerrequisito de conocer el estándar](https://github.com/dotnet/Open-XML-SDK).

## Estado del módulo actual

La implementación está deliberadamente limitada y documenta ese alcance en `docs/guides/INICIO.md`, `docs/architecture/DECISIONES.md` y `docs/architecture/MVP.md`:

- `text_slots` emite un segmento por párrafo y concatena varios `w:t`/`w:r` únicamente si los runs comparten exactamente el mismo `w:rPr`; admite párrafos en `body` y celdas `tc`. Serializa el target en el primer `w:t` y retira los restantes.
- Rechaza formato mixto, hyperlinks, campos, revisiones, content controls, text boxes, dibujos, tabs/br/CR, referencias a notas y comentarios; rechaza texto en historias/partes fuera de `word/document.xml`. Esto evita declarar una pérdida silenciosa, pero excluye muchos documentos Word reales.
- `inspect` impone nombres/rutas/namespace OPC y parte principal convencionales, verifica relaciones y conserva otras entradas ZIP sin volver a serializarlas. Al exportar solo reemplaza el contenido del `w:t` aceptado y vuelve a importar para cotejar los targets; esa comprobación prueba el extractor propio, no que Word abra/renderice sin reparar.
- El modelo `ImportedSegment` guarda source y target planos, sin lista de códigos, runs ni anotaciones inline. Para implementar el editor protegido M2 habrá que ampliar el modelo persistido antes de ampliar el parser/exporter.
- `zip` puede copiar datos comprimidos y metadata de entradas sin recomprimir, pero su propia documentación advierte que el raw-copy no valida metadata/CRC; el diseño actual vuelve a inspeccionar el paquete de salida. No se debe confundir copiar entradas con validar OPC o preservar el layout Word. [zip 4.6.1 `ZipWriter`](https://docs.rs/zip/4.6.1/zip/write/struct.ZipWriter.html).

Referencias locales revisadas: `src/formats/docx.rs`, `src/model.rs`, `tests/docx.rs`, `docs/guides/INICIO.md`, `docs/architecture/MVP.md`, `docs/architecture/DECISIONES.md` y `Cargo.toml`. No se editó código.

## Camino mínimo recomendado

1. **Conservar el formato de transporte actual.** Seguir usando ZIP + streaming XML nativo Rust (`zip` + `quick-xml`), leer/validar la estructura OPC y conservar el paquete original como esqueleto. No hace falta portar Open XML SDK ni cambiar a .NET para cubrir el siguiente incremento. Usar el SDK como referencia de conceptos, no como una promesa de fidelidad ni como solución de render.

2. **Añadir namespace-aware parsing antes de abrir el subset.** Resolver `document.xml` a través de la relación `officeDocument` y content type, y empatar nombres por namespace URI y nombre local. Primero cubrir el Transitional convencional producido por Word; Strict y variantes de paquete deben detectarse y rechazarse con un motivo claro hasta contar con fixtures específicos.

3. **Ampliar el modelo para tags protegidos y el párrafo como unidad lingüística.** Dentro de cada `w:p`, concatenar solo el texto traducible de sus runs para el source visible, guardando una secuencia serializable de fragmentos de texto y códigos inline con identidad/orden: cambios de propiedades `rPr`, bordes, `w:tab`/`w:br` y estructuras admitidas. El editor debe mantener los códigos protegidos y el export reconstruir el texto sobre el esqueleto original sin aplanar formato. Campos, enlaces, controles, revisiones, dibujos/text boxes y contenido no reconocido se dejan fuera del primer incremento o se representan como códigos solo cuando su round-trip tenga regla explícita.

4. **Extender en cortes de bajo riesgo.** Primero varios runs y fragmentación arbitraria del texto, estilos comunes, tablas; luego headers/footers/footnotes/endnotes como historias separadas con ubicación e IDs estables; después hyperlinks y campos con QA de códigos; tracked changes/SDT/drawings en última instancia. Mantener las partes que LumenCAT no edita sin parsear/serializar.

5. **Definir “abre en Word” como aceptación independiente del round-trip propio.** Para cada corte, mantener fixtures de DOCX guardados por Microsoft Word, comparar número/orden de párrafos y texto, verificar que los códigos se conservaron, comprobar que el paquete se reabre y correr una apertura/render real con versión de Word identificada. Validación XSD/OPC y reimportación interna son checks útiles, pero no sustituyen la inspección visual/layout en Word. El corpus debe incluir texto con formato mixto, listas, tablas, campos de página/TOC, enlaces, header/footer, notas, revisiones, texto no latino y translaciones mucho más largas que el origen.

## Bibliotecas Rust observadas

El proyecto ya fija `quick-xml 0.38.3` y `zip 4.6.1`. La API `NsReader` de quick-xml puede resolver namespaces, con la advertencia documentada de que su matching de tags sigue respetando el QName de apertura/cierre. La API `raw_copy_file` de zip permite preservar los bytes comprimidos de entradas inalteradas, aunque no verifica metadata/CRC. Estos son escalones pequeños que reutilizan las dependencias instaladas. [quick-xml 0.38.3](https://docs.rs/quick-xml/0.38.3/quick_xml/reader/struct.NsReader.html), [zip 4.6.1](https://docs.rs/zip/4.6.1/zip/write/struct.ZipWriter.html).

`office_oxide` declara lector/escritor/editor DOCX y capa OPC compartida, pero hoy aparece como `0.1.x`; la documentación del crate no prueba cobertura exhaustiva, edición lossless de markup desconocido ni interoperabilidad con Word. Es candidato a evaluación comparativa con fixtures, no una recomendación para sustituir el camino actual solo por su tabla de features. [API `office_oxide`](https://docs.rs/office_oxide/0.1.12/office_oxide/), [módulo DOCX](https://docs.rs/office_oxide/0.1.12/office_oxide/docx/).

## Límites que deben figurar en el producto

- “Compatible con Word” requiere especificar formatos/constructos y versiones; extensión `.docx` o ZIP válido no definen por sí solos el contrato de fidelidad.
- Round-trip estructural no equivale a render idéntico: el texto traducido puede cambiar saltos de línea, paginación y disposición incluso preservando estilos y recursos.
- Mantener inalteradas partes OPC desconocidas reduce el área de riesgo, pero no garantiza que nuevos elementos/extensions sean semánticamente entendidos por Word.
- Hasta hacer validación visual real, describir el soporte como **subset DOCX Transitional con preservación del esqueleto**, no como round-trip universal ni como compatibilidad probada en Word.
