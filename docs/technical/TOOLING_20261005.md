# Tooling de desarrollo optimizado — 2026-10-05

Estado final del ciclo editar→feedback y de la infraestructura de build, decidido con benchmarks en Ryzen 5 5600G (6C/12T, 16GB, NTFS). Evidencia cruda en `output/tooling-optim-20261005/` (local, no versionada).

## Configuración adoptada

- **Kache 1.0.0** como `rustc-wrapper` **en el config del proyecto** (`.cargo/config.toml`), no global: daemon auto-arrancado, store en `%LOCALAPPDATA%\kache` con tope 20GiB y GC propio (`.kache.toml`). Reutilización entre worktrees medida: **88,3 % hits** (384/435 crates, ~11 min de cómputo evitados); los target dirs hardlinkean al store.
- **nextest 0.9.146** para el fast loop: suite warm **6,7s** vs 21,4s de `cargo test` baseline (y `cargo test` mejoró a 9,2s porque `test` ahora hereda `dev` y comparte artefactos). `cargo test` sigue válido para doctests/casos especiales.
- **`[profile.dev] debug="line-tables-only"`** + deps a `false`: backtraces con líneas en código propio a coste ~0 (+8KB de exe, ±1s en rebuild). `[profile.debugging]` con debuginfo completo e incremental para sesiones de debugger (`cargo dbg`).
- **Aliases**: `cargo fast` (run), `cargo fast-check` (check --all-targets), `cargo fast-test` (nextest), `cargo dbg`.
- Release **intacto**: LLVM + thin-LTO + strip, verificado (7m17s, exe 21,7MB).

## Bootstrap en otra máquina

1. Rust estable ≥1.99 (no se requiere nightly; ninguna feature adoptada la usa).
2. `cargo install kache --locked` — **obligatorio antes de construir**: el proyecto envuelve rustc con kache y `cargo build` falla si el binario no existe. Verificar con `kache doctor`.
3. `cargo install cargo-nextest --locked` — requerido por `cargo fast-test`.

## Decisiones descartadas (con evidencia)

- **Cranelift** (dev): las deps compilan pero el enlace falla — `pulp v0.22.3` (SIMD, transitivo del stack GPUI) deja símbolos plantilla `st_b32s_*` sin resolver (LNK2001) en los 3 bins. Limitación SIMD conocida del backend. No se adoptaron perfiles mixtos porque duplicarían la compilación de las 435 deps.
- **`-Zthreads`**: t8={196,7/223,5}, t6={228,7}, default={218,5}s en cold — la dispersión entre corridas supera las diferencias; el cold está saturado por codegen de deps (`windows` 77s, `image` 21s, familia gpui ~70s), no por el frontend.
- **rust-lld**: el link con MSVC ya cuesta ~0,8–1,0s de un rebuild de ~4s; la ganancia posible queda bajo el ruido, con riesgo conocido en GPUI/Windows. Se mantiene MSVC.
- **incremental=true en dev**: A/B intercalado sin ganancia medible en este crate (4,13 vs 3,91s); se mantiene `false` (menos disco).
- **Pin de nightly**: nada adoptado lo necesita; solo añadiría deriva de clippy al gate `-D warnings`.
- **bacon**: duplicaría el `cargo check` que ya hacen rust-analyzer/agentes.
- Duplicados de dependencias (90, p. ej. bitflags 1/2, gif 0.13/0.14): transitivos de gpui/serde; sin acción rentable sin cambiar librerías.

## Benchmarks (resumen)

| Workflow | Antes | Ahora |
|---|---:|---:|
| Cold (target nuevo, caché vacía) | 237,8s | 294s (puebla) / 225s con caché caliente |
| Warm no-op / check incremental / rebuild 1 archivo | 0,75 / 1,0 / 4,0s | 0,74 / 1,0 / 3,9–6,7s |
| Suite warm | 21,4s | 9,2s (`test`) / 6,7s (nextest) |
| Disco | 14GB target | 4,4GB target + 3,5GB store (tope 20GiB) |

Ruido de la máquina: ráfagas transitorias (±3–6× en mediciones cortas); toda decisión se tomó con repeticiones intercaladas. Recomendación pendiente de aprobación del usuario: excluir `.cache/target` y el store de kache de Windows Defender (reportado como bottleneck, no aplicado).

## Mantenimiento

- `kache stats --last-build` (hit rate), `kache explain` (por qué miss), `kache doctor`. GC automático bajo presión de 20GiB.
- Tras `rustup update` estable, kache re-keya por versión de compilador (re-poblado único).
- No fijar `RUSTFLAGS` globalmente; cambios de flags invalidan claves del cache.
